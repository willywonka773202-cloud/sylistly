### Researched 2026-06-20 — viable NEXT enhancements (device-present session, not blind headless adds)
- **View Transitions API** (richer route/shared-element transitions): RESEARCHED — **same-document VT is Baseline since Oct 2025** (Chrome/Edge 111+, Firefox 133+, Safari 18+) and **Next.js App Router has experimental `viewTransition` support** (next.config `experimental.viewTransition` + a `<ViewTransition>` component); degrades gracefully (unsupported → DOM just updates, no animation). WHY IT MATTERS HERE: the current route transition is OPACITY-ONLY ON PURPOSE — `app/template.tsx`'s comment notes a transform would establish a containing block and break every `position:fixed` element (bottom nav, modals). **View Transitions sidestep that entirely** — they snapshot the old/new page and cross-fade/morph the SNAPSHOTS, not the live DOM, so fixed elements survive. So the "we can't do richer transitions" limitation is now LIFTABLE: e.g. a Discover/feed card morphing into the `/build` page (shared-element), or a directional slide between tabs. WHY NOT DONE BLIND: it's experimental in Next (needs the config flag + wiring), the morph FEEL is unverifiable headless (needs Will's device to tune), and it changes navigation behavior app-wide (test every route + the fixed nav/modals). Verdict: real, modern, on-brand "go all out" — do it in a device-present session. Refs: web.dev VT-baseline, Next.js view-transitions guide.
- **CSS scroll-driven animations** (`animation-timeline: view()`): RESEARCHED current support — landed in **Safari 26** (so it now covers Sylistly's iOS-Safari + Chrome-Android audience), Chromium yes, **Firefox no** (not Baseline yet → must be a progressive enhancement). Win: grid cards (Discover/Browse) animate as they scroll INTO view, driven by scroll position — smoother + "re-alive on scroll" vs the current one-shot IntersectionObserver `Reveal`. WHY NOT DONE BLIND TONIGHT: (1) it conflicts with the existing `Reveal` (both animate entrance opacity/transform) → needs a clean `@supports`-gated swap, not a layer; (2) scroll-driven motion is UNVERIFIABLE headless (no compositor/scroll-driven engine — the documented gotcha) → needs Will's device to tune `animation-range`; (3) Firefox fallback must be the static/Reveal path. Verdict: real, modern, on-brand for "go all out" — do it in a device-present session where the feel is tunable. Refs: WebKit scroll-driven guide, MDN animation-timeline.

Sources: [WebKit: scroll-driven animations](https://webkit.org/blog/17101/a-guide-to-scroll-driven-animations-with-just-css/) · [MDN: animation-timeline](https://developer.mozilla.org/en-US/docs/Web/CSS/animation-timeline)
